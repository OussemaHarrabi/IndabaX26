AegisGraph part 1: shape and contracts

AegisGraph is a small, deterministic HTTP service that reads a SENTINEL decision request, converts the loose wire fields into a strict internal canonical action, and returns exactly one of four verdicts — allow, block, escalate, rewrite — without ever executing the proposed action. It is a reference monitor: a checkpoint that inspects an action and issues a verdict. It never runs a tool, never calls a model, never writes memory.

The one line worth remembering

It is rules, not a model. Every verdict comes from deterministic Python policy code, so the same request always produces the same answer.

Two clarifications that save confusion later:

  • No LLM inside the defense. The only model in the picture is the agent on the harness side, which proposes the candidate actions AegisGraph judges.
  • Nothing is trained. The project never fits weights for the defense.

The canonical action model

The engine never reads JSON. It reads five small frozen classes in contracts.py. Frozen means you cannot change one after it is built — mutating it raises an error, and a test asserts it (tests/test_contracts.py:30, code reading).

Inside CandidateAction, argument values are deliberately flat — str | int | float | bool | None only, no nested objects or lists (backend/aegisgraph/contracts.py:31). The validator at backend/aegisgraph/contracts.py:123-136 then enforces: at most 32 arguments; every key a Python identifier of ≤ 64 chars; every string value ≤ 8 000 chars (MAX_ARGUMENT_CHARS); every float finite (no NaN/inf).

A second validator, _shape_matches_type (backend/aegisgraph/contracts.py:142-161), enforces that the shape matches the type:

  • tool_call needs tool and must not carry content.
  • respond and memory_write need content and must not carry tool/arguments.
  • request_confirmation must wrap a tool_call in confirmation_for.
  • Only respond may set final=True.

Why a second, stricter internal model

contracts.py and sentinel.py describe nearly the same four action types. Keeping both is intentional, because the two sides have opposite jobs.

Wire model: forgiving

The organizer can add a field next season; a defense that crashes on unknown fields would fail closed on every request. So the envelope, provenance records, conversation items, observation view and history digest all use extra="ignore" (backend/aegisgraph/sentinel.py:50-52). A test feeds in future_envelope_field and asserts it is dropped (tests/test_sentinel_adapter.py:52-63, code reading).

Two strict spots on the wire

SentinelCandidateAction — an unknown key inside the action is a hard error, not ignored (backend/aegisgraph/sentinel.py:54-57, test at tests/test_sentinel_adapter.py:65-80) — and SentinelResponse (backend/aegisgraph/sentinel.py:188-191).

Canonical model: strict everywhere

backend/aegisgraph/contracts.py:97-99. By the time the engine runs, every field it can read has been re-checked against canonical bounds. A value that passed the lenient wire parse is parsed again under the canonical rules, so a looser wire type can never smuggle a value the engine was not written to handle.

Two fingerprints, on purpose

The model can produce two different hashes of the same action, and the difference is a designed trade-off.

DigestWhat it is forWhat it normalizes away
action_digest
backend/aegisgraph/contracts.py:249-262		 The confirmation digest: the protocol uses it to match a human approval to a later execution. Argument keys sorted; whitespace inside strings collapsed; an integral float like 12.0 becomes 12; final ignored.
exact_action_digest
backend/aegisgraph/contracts.py:265-285		 The execution fingerprint: recovers the precision the protocol threw away, for audit. Nothing — it keeps final, keeps raw argument text, and recurses into confirmation_for.

A test pins the normalization with an official golden vector: {amount: 12.0, note: "a b\n c"} and {amount: 12, note: "a b c"} both hash to 2ce0b8de5d0b516fd176a716 (tests/test_contracts.py:52, measured). Another test shows a non-final and a final respond share an action_digest but differ under execution_digest (tests/test_contracts.py:80).

The practical trap

The normalization is lossy by design — it is what the protocol asked for. [INFERENCE] Anything that binds only action_digest inherits that loss: two genuinely different executions can share a confirmation signature. exact_action_digest exists to mitigate this, and the code comments the behaviour as intentional.

Provenance resolution: where trust comes from

Provenance is the audit trail that says where a piece of text came from and how much it should be trusted. On the wire it is a list of records the request cites by id (backend/aegisgraph/sentinel.py:123-125). The adapter's central job is to turn each cited id into a trust label on an Observation, so the engine can later compare "untrusted content" against "trusted sink".

The adapter builds an index of provenance records once (backend/aegisgraph/adapter.py:43-47), then walks every conversation item plus the single observation through one function, append_resolved (backend/aegisgraph/adapter.py:54-93). Three cases matter.

Case 1 — a cited id that resolves

The item has provenance_ids: ["prov-1"], and prov-1 exists. The adapter copies the trust level and sensitivity verbatim from the wire record and mints an observation whose source is <id>:<source_type>:<source_id> (backend/aegisgraph/adapter.py:83-93).

Honesty note: nothing here verifies the declared label against the actual origin. [INFERENCE] The whole trust model rests on the harness honestly labelling its own sources. That is an assumption the design chooses, not a cryptographic guarantee.

Case 2 — an id that is missing or duplicated

If the cited id is not in the index, records.get(identifier) returns None, the adapter marks the whole request incomplete (complete = False), and it emits an observation labelled source="unresolved:<id>", trust_level=adversary_controlled, sensitivity=restricted (backend/aegisgraph/adapter.py:75-80, helper at backend/aegisgraph/adapter.py:151-159). The engine then returns a block with PROVENANCE_INCOMPLETE (backend/aegisgraph/engine.py:467-468), regardless of what the candidate action was.

Duplicates take the same path: the index is built with records[record.id] = None if record.id in records else record (backend/aegisgraph/adapter.py:47), so a repeated id overwrites the real record with None and any later citation of it is treated as unresolved. [INFERENCE] Fail-closed, but the first record is silently discarded and no error names the duplicate — the id simply becomes indistinguishable from "never declared".

Case 3 — no ids, and the implicit-trust rule

This is the case worth slowing down for. If a conversation item carries no provenance_ids, the adapter does not mark it unresolved. It looks at the item's role and mints a label (backend/aegisgraph/adapter.py:56-67).

Role, with no idsResulting trustsource string
userauthenticated_userimplicit:user
agent, safety, humantrusted_internalimplicit:<role>
anything else (tool, memory, observation)untrusted_internalunattributed:<role>

The contrast is the finding. An explicit id that fails to resolve becomes adversary_controlled and blocks the request. An item that simply omits its ids can be auto-promoted to authenticated_user — and the omission is not recorded as incomplete.

Audit finding: trust is self-asserted in this path
  • The wire client chooses the role (backend/aegisgraph/sentinel.py:129) and chooses whether to include provenance_ids.
  • So a client can present attacker-influenced text under role="user" with no ids and have it trusted as if a real authenticated user wrote it (backend/aegisgraph/adapter.py:55-68).
  • The code's docstring frames the intent as deliberate — evidence supplied without provenance identifiers "remains usable but is marked unattributed and untrusted rather than being confused with a broken integrity reference" (backend/aegisgraph/adapter.py:40-43). That holds for the tool/memory branch, but the user/agent/safety/human branch does the opposite of "untrusted": it widens trust.
  • [INFERENCE] Likely rationale: a legitimate harness always labels turn text as user. The cost is that the defense cannot distinguish a well-labelled turn from a self-labelled attack.

Everything else the adapter decides

Beyond the three cases, adapt_request also (backend/aegisgraph/adapter.py:107-134):

  • Computes least_trust and max_sensitivity across all observations — defaults authenticated_user / internal when there are none (backend/aegisgraph/adapter.py:107-116). These become the metadata on the response.
  • Derives a canonical request_id as "request:" + sha256(run_id + "\x00" + step_id)[:32] (backend/aegisgraph/adapter.py:120, helper at backend/aegisgraph/adapter.py:178-181).
  • Replaces an empty user_goal with the literal "Unspecified user goal" (backend/aegisgraph/adapter.py:121). The wire model permits an empty goal; the canonical model requires non-empty (backend/aegisgraph/sentinel.py:164 vs backend/aegisgraph/contracts.py:180), so the mismatch is smoothed over rather than rejected.
  • Normalizes kind to fit the canonical pattern with _safe_kind (backend/aegisgraph/adapter.py:171-176): lowercase, non-conforming characters become _, truncate to 64. [INFERENCE] This is lossy — two distinct wire kind values could collapse into one canonical value, with no collision check.
  • Compacts any source string longer than 256 chars into source:<sha256> (backend/aegisgraph/adapter.py:183-187).

Bounded, fail-closed I/O

Fail closed means: when something is wrong or unknown, the system picks the safe outcome (block), never the permissive one (allow). AegisGraph applies this at several layers.

Every string, map and list a request can carry has a ceiling (backend/aegisgraph/contracts.py:25-29; wire mirrors at backend/aegisgraph/sentinel.py:54-108, backend/aegisgraph/sentinel.py:176-181).

The 128-observation truncation

A request can carry many conversation items and each may cite several provenance ids, so the observation count can exceed the canonical cap of 128. The adapter does not reject — it selects. _select_security_relevant_observations (backend/aegisgraph/adapter.py:190-206) ranks observations by (-trust_index, -sensitivity_index, original_index), keeps the 128 least trusted and most sensitive, then restores their original order. When it must drop evidence, it drops the benign evidence and keeps the suspicious evidence.

"Keeps the suspicious ones" is a heuristic, not a proof. [INFERENCE] A benign-but-relevant item can vanish, and the only trace left is the boolean evidence_truncated = len(observations) > 128 (backend/aegisgraph/adapter.py:133). The engine consumes that flag as a block with EVIDENCE_TRUNCATED (backend/aegisgraph/engine.py:471-472).

Generic error bodies

Malformed input never leaks field names or values. The app installs a handler that turns any request-validation error into the constant body {"detail": "Invalid SENTINEL request"} with status 422 (backend/aegisgraph/app.py:65-67), and routing errors into either that constant or {"detail": "Request could not be safely processed"} with the original status (backend/aegisgraph/app.py:70-75). A test plants a secret in a bad request and asserts it does not come back (tests/test_http_service.py:110, code reading).

The 64 KB response cap with a block fallback

After a decision is built, the app serializes it and checks the byte length against _MAX_RESPONSE_BYTES = 64_000 (backend/aegisgraph/app.py:20, backend/aegisgraph/app.py:91-92). It is reachable in principle, because a rewrite can carry a tool_call with 32 arguments of 8 000 characters each. If the response is too large, it is not sent.

Instead, any exception while building or validating the response falls into one catch-all returning HTTP 200 with a fixed block (backend/aegisgraph/app.py:94-105): risk_score = 1.0, confidence = 1.0, reason_codes = ("INTERNAL_EVALUATION_FAILED",). The comment states the invariant directly: "A valid request reaching policy must never become an allow on an error" (backend/aegisgraph/app.py:96).

The same bound appears on the organizer side — the harness treats a body over 64 000 bytes as a defense failure (.sentinel_reference/src/sentinel/defenses/client.py:14,78), so the two ends agree.

The service surface

The entire HTTP surface is one 116-line file (app.py).

Each design choice has a reason:

  • No authentication. No API key, session, or auth middleware anywhere in the package. This is documented, not hidden: the README says the service "has no authentication by default and must not be exposed directly to an untrusted network" (README.md:155-157) and to "keep it bound to localhost" (README.md:134). It is a local prototype by intent.
  • Local-only binding. The documented run command binds loopback explicitly: --host 127.0.0.1 --port 8080 (README.md:125).
  • Docs disabled. docs_url=None, redoc_url=None, openapi_url=None (backend/aegisgraph/app.py:30-35), so /docs and /openapi.json return 404 — asserted in tests/test_http_service.py:40-46.
  • Security headers. Every response gets Cache-Control: no-store, Pragma: no-cache, X-Content-Type-Options: nosniff (backend/aegisgraph/app.py:57-59); the HTML asset additionally gets a strict Content-Security-Policy including connect-src 'none' (backend/aegisgraph/app.py:24-28, backend/aegisgraph/app.py:60-61).
  • Client-side-only dashboard. It reads files you pick and never uploads them (static/index.html:36), has hard limits of 25 MiB per file and 100 000 events (static/dashboard.js:4-5), and persists nothing.

Two places where docs and code disagree

"Documented prototype" and "documented prototype with a footgun" are different things, so both are stated plainly.

1. The Docker port publish contradicts the localhost rule

The README tells you to keep the unauthenticated service bound to localhost (README.md:134), then a few paragraphs later gives docker run ... -p 8080:8080 (README.md:168). -p 8080:8080 publishes the port on all host interfaces, not just loopback. With no authentication, that is the one concrete deployment mistake in the packaging. The fix is -p 127.0.0.1:8080:8080. [INFERENCE] This is a documentation defect, not a code defect — the app cannot control how a container is published.

2. No HTTP-layer request-body cap

Per-field pydantic bounds exist, but nothing inspects Content-Length and no middleware limits the body. A worst-case accepted body is roughly 256 conversation items × 16 000 chars plus provenance and context — on the order of a few megabytes, buffered in full before validation. [INFERENCE] A single large POST can pin memory; no test covers it.

Neither is a hidden vulnerability; both are places where the code is looser than the prose implies. Naming them is the honest move.

Why this design is auditable

The architecture is deliberately boring, and boring is what you want from a security component you must defend to a jury.

Purity and determinism

The decision path holds no server-side state: no session, no cache, no run store, nothing written to disk. Each request is evaluated independently. Combined with rule-based (not model-based) policy, that gives "same request in, same decision out". [INFERENCE] Statelessness is a structural fact (no module-level mutable state in engine.py/policy.py/adapter.py), though no test asserts it.

Explicit reason codes

Every verdict carries machine-readable reason_codes in a fixed UPPER_SNAKE vocabulary, so a reviewer can tell why without reading the explanation text. The vocabulary is defined by a single pattern, so a stray free-text code becomes a validation failure rather than a leak.

Hashes that pin the revision

The canonical request id is a content hash of run_id and step_id (backend/aegisgraph/adapter.py:178-181), and the two action digests bind the exact action semantics. Together with the evaluator's own deterministic digest, these let you prove which revision produced a given measured result — which is why Chapter 8 can talk about "the v5 revision" and mean one specific artifact.

That is the through-line for the rest of the course: a small transparent pipeline (this chapter), a rules engine with explicit reason codes (Chapter 7), and evidence that pins exactly what was measured (Chapter 8).

Check yourself

In one sentence, what does AegisGraph return for each candidate action, and what does it never do?
It returns exactly one of allow, block, escalate, rewrite for the proposed action; it never executes that action (backend/aegisgraph/app.py:85).
Why keep a separate canonical model in contracts.py instead of trusting the wire types in sentinel.py?
The wire model must be forgiving (extra="ignore") for forward compatibility, while the canonical model is strict and bounded everywhere (backend/aegisgraph/contracts.py:97-99). Re-validating into canonical types means the engine only ever reads fields that passed the strict bounds, and the engine stays free of wire coupling.
A request cites provenance_ids: ["prov-x"] and prov-x is not in provenance. What trust does the observation get, and what does the engine do?
The observation is labelled unresolved:prov-x, adversary_controlled, restricted, and the request is marked incomplete (backend/aegisgraph/adapter.py:75-80); the engine returns a block with PROVENANCE_INCOMPLETE (backend/aegisgraph/engine.py:467-468).
Now the same request cites no ids at all, with role="user". What changes?
The observation is labelled implicit:user with trust authenticated_user and is not marked incomplete (backend/aegisgraph/adapter.py:56-67). This is the trust-widening finding: the client chose both the role and the omission, so the trust is self-asserted.
What does the 128-observation truncation keep, and what flag does it set?
It keeps the 128 least-trusted, most-sensitive observations, re-sorted to their original order (backend/aegisgraph/adapter.py:190-206), and sets evidence_truncated = True when observations exceeded 128 (backend/aegisgraph/adapter.py:133). The engine then blocks with EVIDENCE_TRUNCATED (backend/aegisgraph/engine.py:471-472).
A rewrite decision would produce a response larger than 64 KB. What is sent?
Not the oversized response: the size check raises (backend/aegisgraph/app.py:91-92) and the endpoint returns a fixed HTTP 200 block with risk_score = 1.0, confidence = 1.0, INTERNAL_EVALUATION_FAILED (backend/aegisgraph/app.py:94-105).
Why are action_digest and exact_action_digest different?
action_digest is the protocol's confirmation digest and normalizes whitespace, integral floats and ignores final (backend/aegisgraph/contracts.py:249-262, backend/aegisgraph/contracts.py:287-292); exact_action_digest keeps those distinctions so a confirmation signature can never stand in for an exact execution fingerprint (backend/aegisgraph/contracts.py:265-285).
