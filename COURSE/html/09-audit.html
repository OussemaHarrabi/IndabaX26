Audit findings and the honest verdict

This chapter is the audit: what was independently verified, what is fragile, what it costs, what to fix first — and a straight answer to "can this win?".

How the audit was done

  1. Recomputed the evidence. Every metric key and per-domain slice of all ten scorecards was recomputed from the raw outcomes[] arrays without using the project's own metric code.
  2. Re-hashed the artifacts. All fourteen claimed SHA-256 digests were recomputed from the bytes on disk, and the evaluator's deterministic digest algorithm was reimplemented from its description.
  3. Re-read the implementation — every code claim below carries an anchor that was opened and checked.
  4. Re-ran the greps behind the project's strongest honesty claim (no scenario-id-specific decisions) and behind several "dead code" findings.
  5. Ran the service and attacked it with hand-written requests, which produced the two findings marked "demonstrated live".

Severity below: S1 breaks a claim or leaves a real bypass; S2 costs rubric points, misleads a reader, or blocks reproducibility; S3 hygiene.

The three findings that matter

F1 — the trust boundary is asserted by the caller

Four requests were sent to the running service during this audit. The only difference between the blocked and the allowed case is which channel the text arrived on:

RequestArrival channelResult
hostile instruction in a tool result, cited by provenance id, repeated in the action's texttool observation with provenance_idsblock UNTRUSTED_INSTRUCTION risk 0.99
the same instruction in a user-role item with no provenance idsrole-asserted trustallow POLICY_CHECKS_PASSED authenticated_user
the same instruction written to memory from a safety-role itemrole-asserted trustallow, metadata records memory_trust: trusted_internal
control: the same memory write with untrusted provenancetool observation with provenance_idsallow UNTRUSTED_MEMORY_INHERITED untrusted_external

In the pinned harness the attacker mutates declared text surfaces, which carry provenance, so the published threat model is not bypassed. The weakness is at the contract boundary: the component meant to enforce the trust boundary accepts a self-declaration of trust from the component it guards. The fix that preserves utility is not "trust nothing" — it is to require an explicit provenance id, or an explicit harness-level opt-in, before text counts as authenticated intent.

F2 — a rewrite guard only tests exercise

Grep confirms validate_rewrite() has no caller outside the test suite. The served path is not unguarded — the engine re-validates its own replacements inside the two redaction functions, and this audit observed REDACTION_REVALIDATION_FAILED returned by the running service — but the dead helper is the one that looks authoritative. Wire it in or delete it; do not leave a reviewer guessing which mechanism protects a substitution.

F15 — a rewrite that should escalate becomes a hard block

Revalidation accepts exactly one outcome: allow. Take an internal email whose body quotes a credential from a confidential record: the engine redacts it (correct), re-evaluates the replacement, which is still consequential and still unconfirmed, so the inner verdict is escalate — and the outer decision collapses to a block at risk 1.0. Demonstrated live. The security intent is defensible; the utility cost is invisible in the docs and is a plausible contributor to the residual false-block rate. The cheap fix is to propagate the inner escalate for the redacted action.

Seven of nine items are honesty and finish work, not new defence logic. That is the normal shape of an agent-built project under a measured-evidence discipline: the risk is never the arithmetic, it is the gap between what the docs imply and what the code does.

What would falsify the project's claims

The defensible claim is narrow and specific: on SENTINEL's published 40-scenario suite, with the pinned kit and Qwen3-8B at temperature 0 and seed 0, this deterministic gateway reduced attack success on the 22 attacks a real model reaches from 22/22 to 0/22, at a 0.86 % false-block rate and 9.3 ms p95 latency, losing one benign task relative to the undefended baseline.

  • Rerun across seeds — would show whether 0/22 is a stable property or one observation.
  • A paraphrase / translation / encoding suite — would test the claim that the rules generalise beyond the literal attack vocabulary (chapter 7 names the blind spots).
  • AgentDojo — would test generalisation beyond this benchmark; it is the optional bonus track and nobody has run it here.
  • A benign regression suite before and after any rule change — would test whether the 0.86 % cost is stable.
  • A stronger or less quantised model — would test whether 22/22 reachability is a property of the attack set or of Qwen3-8B at Q4_K_M.
  • A new injection surface (a tool argument the suite never uses, a non-email sink) — would test whether the flow rules are family-complete.

My call

As submitted today: unlikely to place. Not because the defence is weak — it is the strongest artefact in the repository — but because 40 of 100 points are in a video that does not exist, the report a judge is told to read first is missing, and a solo entry may not even be eligible under a 3-5 member rule.

With three things fixed — a recorded 5-10 minute trace demo, the compiled report committed, and eligibility confirmed in writing — this is a credible top-8 pitch candidate, because most teams will show a defence and a score, while this one can show a falsifiable claim, an ablation and an admitted failure. That is exactly what the report rubric asks for, and it is rare.

Caveat, honestly: I cannot see the other submissions, the judging is human, and "top-8" is a ranking against unknown competition. What I can say with evidence is which rubric categories are currently claimed and which are not — that table above.

Where to take your learning next

  • AgentDojo (NeurIPS 2024) — an independent prompt-injection benchmark for tool-using agents; the highest-value generalisation experiment available.
  • OWASP Top 10 for LLM Applications — read LLM01 (prompt injection) and LLM06 (excessive agency) with this project in mind; you will recognise every design decision.
  • Dual-LLM / planner-executor patterns — the architectural answer to "the model reads untrusted text", complementary to this project's decision-point answer.
  • Taint tracking and information-flow control — the academic ancestor of these rules; the provenance baseline's failure is the classic precision problem of dynamic taint analysis.
  • Calibration — why reporting Brier/ECE requires a score that means something (F5).

Check yourself

Which parts of the project were independently recomputed, and which were only read?
All ten scorecards' metrics and per-domain slices, all claimed hashes, the evaluator digest, the reached-attack set and the decision counts were recomputed from artifacts. Source-code claims are code reading; structural blind spots are marked INFERENCE.
Why is F1 serious even though the published suite cannot exploit it?
Because the defence's trust boundary accepts a self-declaration from the client it is meant to guard. Exploitability depends on the deployment; the design weakness does not.
What is dead in F2, and what is not?
validate_rewrite() and the codes only it emits never run in production. The pipeline's own revalidation is live — this audit saw REDACTION_REVALIDATION_FAILED come back from the running service.
What does F15 change about a redacted consequential action?
Revalidation accepts only allow, so an action that would have been escalated for human confirmation becomes a hard block once a secret is found inside it.
Why is the denominator 22 rather than 31?
Nine attacks never produce their harm even with no defence installed, so their zero is not evidence about any defence. The reachability control is what identifies them.
Which rubric category is the biggest risk right now, and why?
Video and observability — 40 points, and no video exists. The defence being excellent does not claim a single point in that category.
Name three experiments that would falsify the project's central claim.
A multi-seed rerun, a paraphrase/translation attack suite, AgentDojo, a benign regression suite, a stronger model, or a new injection surface — any one can shrink the claim.
